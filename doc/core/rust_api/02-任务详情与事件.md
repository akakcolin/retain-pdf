# 任务详情与事件

这篇讲任务执行过程怎么读。

## 主接口

任务详情：

- `GET /api/v1/jobs/{job_id}`

事件流：

- `GET /api/v1/jobs/{job_id}/events`
- `GET /api/v1/ocr/jobs/{job_id}/events`

失败诊断与恢复：

- `GET /api/v1/jobs/{job_id}/diagnostics`
- `GET /api/v1/jobs/{job_id}/resume-plan`
- `POST /api/v1/jobs/{job_id}/resume`

## 任务详情里该看什么

重点字段：

- `status`
- `display_stage`
- `stage`
- `substage`
- `lane`
- `stage_detail`
- `progress`
- `stage_snapshot`
- `background_snapshots`
- `stages`
- `runtime`
- `failure`
- `failure_diagnostic`
- `timestamps`
- `actions`
- `artifacts`
- `ocr_job`
- `invocation`
- `normalization_summary`
- `glossary_summary`
- `log_tail`

推荐前端用法：

- 当前主状态只看 `stage_snapshot`
- 阶段面板状态看 `stages`
- 事件流只做历史、时间线和排障
- 当前阶段说明看 `stage_detail`
- `stage` 是后端内部机器阶段，不作为前端大阶段判断依据
- 当前任务真阶段看 `runtime.current_stage`
- 总耗时看 `runtime.total_elapsed_ms`
- 当前阶段耗时看 `runtime.active_stage_elapsed_ms`
- 过程时间线看 `runtime.stage_history`

## 请求与协议摘要

`request_payload` 是后端为该任务实际保存的请求参数快照。联调时确认某个参数有没有进后端，优先看这里：

- OCR 页码范围：`data.request_payload.ocr.page_ranges`
- 公式翻译模式：`data.request_payload.translation.math_mode`

`invocation` 回答「这个任务到底走的是旧路径还是当前 stage spec 路径」：

```json
{
  "stage": "provider",
  "input_protocol": "stage_spec",
  "stage_spec_schema_version": "provider.stage.v1"
}
```

- `input_protocol=stage_spec` 说明走的是当前 spec-only worker
- 拿不到不一定是接口坏了，也可能是历史任务没留摘要

`normalization_summary` 是轻量摘要，不是完整报告：

- 字段：`provider` / `detected_provider` / `schema` / `schema_version` / `document_defaults` / `page_defaults` / `block_defaults` / `page_count` / `block_count`
- 当前主链只接受 `schema_version=1.1`
- `*_defaults` 表示默认值收口数量，不再叫 `compat_*`
- 页面展示只读摘要；真要排查 adapter/defaults/validation 细节，下载 `artifacts.normalization_report`

`glossary_summary` 回答「术语表是否启用、命中与未命中情况如何」。

`translation.math_mode` 两个值：

- `placeholder`：默认值，继续走旧的公式保护 / placeholder / 恢复链路
- `direct_typst`：实验模式，不做公式 placeholder 保护，直接让模型输出正文和 `$...$` 数学

前端只需按字符串展示或透传，不需要自己推断。

## 时间线真源

`runtime.stage_history` 是主时间线真源，不要从 `/events` 反推。

每一项通常包含：

- `stage`
- `detail`
- `enter_at`
- `exit_at`
- `duration_ms`
- `terminal_status`

## 事件流怎么读

事件流适合状态卡、进度展示和排障，不是主时间线。主时间线仍看 `runtime.stage_history`。

`GET /api/v1/jobs/{job_id}/events` 返回的是 Rust canonicalize 后的公共事件，不是 Python 原始事件。公共事件里：

- `display_stage` 是阶段快照/事件里的用户阶段，只能是 `ocr | translation | render | null`，永远不会是 `done`。
- `stage` 是后端内部机器阶段，例如 `ocr_processing`、`translating`、`rendering`。
- `substage` 是机器可读子阶段，例如 `translation_batches`、`render_prewarm`。
- `lane` 区分主进度和后台/产物/诊断事件。
- `event_type` 是归一化事件类型，例如 `progress`、`artifact`、`terminal`、`error`、`diagnostic`。
- `message` / `stage_detail` 只给人看，前端不要靠它们判断阶段。
- 原始 Python `stage` / `user_stage` / `event_type` 会保存在 `payload.raw_stage`、`payload.raw_user_stage`、`payload.raw_event_type` 中，排障时再看。

事件项稳定字段：

- `seq`
- `ts`
- `created_at`
- `level`
- `lane`
- `display_stage`
- `stage`
- `substage`
- `stage_detail`
- `event`
- `event_type`
- `raw_event_type`
- `progress`
- `message`
- `provider`
- `provider_stage`
- `payload`

`progress` 是公共进度对象：

```json
{
  "unit": "page",
  "current": 37,
  "total": 142,
  "percent": 26.056338028169012
}
```

前端状态卡优先消费：

- `display_stage`
- `lane`
- `substage`
- `stage_detail`
- `event_type`
- `progress.unit`
- `progress.current`
- `progress.total`
- `progress.percent`

不要优先消费这些内部/兼容字段：

- `payload.raw_stage`
- `payload.raw_user_stage`
- `payload.raw_event_type`
- `message`
- `provider_stage`

`lane` 用来区分主进度和后台事件：

- `main`：主状态卡可展示。
- `background`：后台预热、后台准备等，不应覆盖主阶段。
- `artifact`：产物发布。
- `diagnostic`：诊断或错误辅助信息。

当前稳定子阶段：

| 公共阶段 | 子阶段 | 进度单位 | 说明 |
| --- | --- | --- | --- |
| `ocr` | `ocr_processing` | `page` | OCR 解析页进度；如果 provider 只能返回完成态，则至少给总页数。 |
| `ocr` | `normalizing` | `step` | OCR 结果标准化。 |
| `translation` | `translation_prepare` | `step` | 翻译准备。 |
| `translation` | `domain_inference` | `step` | 文档领域识别。 |
| `translation` | `page_policies` | `page` | 页面策略和块分类。 |
| `translation` | `continuation_review` | `page` | 跨栏/跨页连续段复核。 |
| `translation` | `translation_batches` | `batch` | 主翻译批次。 |
| `translation` | `translation_tail_retry` | `batch` | 尾部重试队列。 |
| `translation` | `garbled_repair` | `page` | 乱码候选段修复。 |
| `translation` | `agent_repair` | `page` | 翻译结果修复。 |
| `translation` | `final_untranslated_recovery` | `page` | 最终未翻译收口。 |
| `render` | `render_prepare` | `step` | 渲染准备。 |
| `render` | `render_prewarm` | `step` | 渲染预热；通常是 `lane=background`。 |
| `render` | `render_pages` | `page` | 页面构建、清理、覆盖、Typst source 生成。 |
| `render` | `render_compile` | `step` | Typst 编译、PDF 保存等不可按页拆分步骤。 |

进度规则：

- 同一个 `stage + substage + progress.unit` 下，`progress.current` 不应倒退。
- `render_compile` 这类 step 进度不要显示成“共 N 页”。
- `render_prewarm` 属于后台 lane，不应覆盖 `render_pages` 的主进度。
- 完成态事件应尽量带最终 `current=total`，方便刷新后恢复状态。

## 生命周期

常见 workflow：

- `book`
- `ocr`
- `translate`
- `render`

workflow 说明：

- `book`：OCR -> Normalize -> Translate -> Render，完整主链路
- `ocr`：只跑 OCR/Normalize，产出 `document.v1.json`，用 `/api/v1/ocr/jobs` 独立入口提交
- `translate`：OCR -> Normalize -> Translate，停在翻译产物，不进入渲染
- `render`：复用已有 job artifacts，只重跑渲染

`book` 和 `translate` 会产生一个 OCR 子任务 `{job_id}-ocr`，好处是 OCR transport 与主链路分开观察、provider 诊断单独挂在详情里返回。

请求侧区分靠两件事：

- `workflow`：决定完整 / OCR-only / Translate-only / Render-only
- `source`：`upload_id`（`book` / `translate`）、`artifact_job_id`（`render`，复用 `source_pdf` 与 `translations_dir`）

`/api/v1/jobs` 的 JSON 请求体以 `source / ocr / translation / render / runtime` 分组结构为正式契约；历史扁平字段只保留在少数 multipart 辅助入口。

前端理解分三层：`status`（任务是否结束）、`stage`（当前在哪个阶段）、`stage_detail`（当前阶段的人类说明）。

常见主阶段：

- `queued`
- `ocr_submitting`
- `ocr_processing`
- `normalizing`
- `translation_prepare`
- `translating`
- `render_prepare`
- `render_preprocess`
- `rendering`
- `saving`
- `finished`
- `failed`

## 失败协议

失败时优先看：

- `failure.summary`
- `failure.category`
- `failure.root_cause`
- `failure.retryable`
- `failure.suggestion`

兼容字段：

- `failure_diagnostic`
- `log_tail`

前端如果只需要任务详情页的干净失败信息，优先读：

`GET /api/v1/jobs/{job_id}/diagnostics`

返回字段：

- `failed_stage`
- `failed_substage`
- `summary`
- `detail`
- `suggestion`
- `retryable`
- `resume_available`

这个接口会复用 `failure` 的正式字段，并在必要时回退到后端分类器，不要求前端自己解析 `request_payload`、`events` 或 `log_tail`。

## 断点恢复

恢复计划：

`GET /api/v1/jobs/{job_id}/resume-plan`

返回字段：

- `can_resume`
- `job_id`
- `from_stage`
- `resume_workflow`
- `reuses_artifacts`
- `reruns_stages`
- `reason`

当前规则：

- 有 `translations_dir + source_pdf`：`from_stage=render`，`resume_workflow=render`，只重跑渲染。
- 有 `normalized_document_json + source_pdf`：`from_stage=translate`，`resume_workflow=book`，重跑翻译和渲染。
- 两类 checkpoint 都没有：`can_resume=false`，`reason` 给出原因。

执行恢复：

`POST /api/v1/jobs/{job_id}/resume`

当前实现复用 `/rerun` 的执行契约：

- 可原地重渲染时，保留原 `job_id`，清空旧渲染产物，排队 `render` workflow。
- 只有 OCR checkpoint 时，创建新的 `book` 恢复任务。
- 如果任务仍在 `queued` / `running`，会返回状态冲突，需要先取消。

## 历史任务缺字段

`runtime = null` 只表示这条任务创建和执行时，后端还没有把运行态时间线持久化到数据库。它不表示前端读错、后端坏了或写入失败，这类任务应视为「历史数据缺失」。

不要和「旧任务被拒绝」混淆：

- `runtime = null`：历史任务数据缺失，详情、事件流仍可能可看
- 详情/下载接口直接提示旧任务不支持：任务停留在旧目录布局（`originPDF/jsonPDF/transPDF/typstPDF`）或旧版绝对路径 artifact 存储，当前后端不会再做兼容迁移，只能重跑

## 排错

先直接用 curl 看原始响应，不要先猜前端：

```bash
curl -s http://127.0.0.1:41000/api/v1/jobs/<job_id> \
  -H 'X-API-Key: your-key'
curl -s 'http://127.0.0.1:41000/api/v1/jobs/<job_id>/events?limit=50&offset=0' \
  -H 'X-API-Key: your-key'
```

原始响应有值而页面没有，优先查前端解包路径。事件流为空时依次检查：接口是否 `200` -> `data.items` 是否非空 -> 是否错读为顶层 `items`。

磁盘排查位置（任务根目录 `DATA_ROOT/jobs/{job_id}/`）：

- `specs/`：当前 worker 真正执行的 stage spec 输入协议；这里不存在但以为是新任务，先排查是不是旧产物或半成品目录
- `logs/events.jsonl`：事件流落盘
- `logs/failure-ai-diagnosis.request.json` / `response.json`：仅主失败类别仍为 `unknown` 且后端成功触发 AI 补充诊断时出现；没有不代表失败分类坏了
- `artifacts/pipeline_summary.json`、`ocr/`、`translated/`、`rendered/`

失败归因读取顺序：

1. `failure.summary`
2. `failure.root_cause`
3. `failure.suggestion`
4. `failure.raw_diagnostic`（回答「原始异常到底是什么」）
5. `failure.ai_diagnostic`（回答「规则没识别出来时 AI 认为大概率是什么」）

`failure_diagnostic` 只是兼容旧字段，不要再当主真源。事件流里失败相关重点事件：`failure_classified`、`failure_ai_diagnosed`（仅 unknown 失败可能出现）、`job_terminal`。

OCR 页码范围联调：

- 字段位置：`POST /api/v1/jobs` 请求体 `{"ocr": {"page_ranges": "1-5"}}`；空字符串表示不限制
- `provider=mineru` 时本地上传会先裁剪子集 PDF 再上传；生效后 `source_pdf`、翻译页码、最终渲染 PDF 都应只覆盖这个子集
- 怀疑没生效，按三层查：`request_payload.ocr.page_ranges` -> 数据库 `jobs.request_json.$.ocr.page_ranges` -> provider 执行日志

`math_mode` 联调：

- `placeholder` 下出现 placeholder 校验、公式分段、windowed formula 属于预期
- `direct_typst` 下重点应看模型直出质量、英文残留和渲染兼容

## 关键结论

- 详情页主接口是 `GET /api/v1/jobs/{job_id}`
- 时间线看 `runtime.stage_history`
- 事件流看 `GET /api/v1/jobs/{job_id}/events`
- 失败真源看 `failure`
- 简洁失败信息看 `GET /api/v1/jobs/{job_id}/diagnostics`
- 恢复按钮状态看 `GET /api/v1/jobs/{job_id}/resume-plan`
